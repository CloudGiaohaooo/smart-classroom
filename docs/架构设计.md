# 架构设计说明

## 一、分层架构

系统采用经典的三层架构 + 前后端分离：

```
Controller（接口层）  →  接收请求、参数校验（@Valid）、返回统一 Result
      ↓
Service（业务层）    →  业务逻辑、事务控制（@Transactional）、权限判断
      ↓
Mapper（数据访问层） →  MyBatis-Plus BaseMapper + 自定义 SQL（@Select 多表 JOIN）
      ↓
MySQL（数据库层）
```

各层职责单一、依赖向下，便于测试与替换（例如 Mapper 层可替换为 JPA 或手写 SQL）。

## 二、请求处理流程（以「作业批阅」为例）

1. 前端 `PUT /api/submissions/1/grade`，请求头携带 JWT；
2. `JwtAuthenticationFilter`（Spring Security 过滤链）解析 token，校验通过后把用户信息写入 `UserContext`（ThreadLocal），并把 RBAC 权限编码写入 `SecurityContext`；
3. `SubmissionController.grade` 接收 `GradeDTO`，`@Valid` 校验参数；
4. `SubmissionService.grade` 执行业务校验（分数是否超满分），在 `@Transactional` 事务内更新提交记录；
5. 返回统一 `Result`，前端解包并刷新列表。

## 三、安全设计

| 机制 | 说明 |
| --- | --- |
| 密码加密 | BCrypt 单向哈希，数据库不存明文；每次登录动态比对 |
| JWT 认证 | 无状态令牌，含 userId、role、过期时间；HS256 签名防篡改 |
| Spring Security 过滤链 + RBAC | `JwtAuthenticationFilter` 认证 + `@PreAuthorize` 方法级授权，四表权限模型（sys_role / sys_permission / sys_user_role / sys_role_permission） |
| ThreadLocal 上下文 | 每个请求线程隔离存储当前用户，请求结束 `clear()` 清理，防内存泄漏 |
| 敏感信息隔离 | VO 层不返回 password 字段 |
| 文件上传 | 按课程分目录、UUID 重命名防覆盖/路径穿越 |

## 四、关键设计决策

1. **为什么用 MyBatis-Plus 而非 JPA？**
   - 对多表复杂 SQL 更灵活（本项目的 JOIN 查询即为例证）；
   - 内置分页插件、`BaseMapper` 通用 CRUD，减少样板代码；
   - 更贴近国内企业主流技术栈。

2. **为什么最终选择 Spring Security 过滤链 + JWT（而非纯拦截器）？**
   - 拦截器工作在 MVC 层，只能做「是否登录」的粗粒度判断；过滤链在进入 MVC 前完成认证，可拿到完整请求上下文；
   - 配合 `@EnableMethodSecurity` + `@PreAuthorize` 实现方法级细粒度授权（如「仅 TEACHER 可 `submission:grade`」）；
   - 权限编码实时从 RBAC 表加载，权限变更即时生效，无需重发 token。

3. **为什么文件存本地而非对象存储？**
   - 教学演示项目，本地落盘零依赖、开箱即用；
   - 通过 `WebMvcConfigurer` 静态映射即可访问；
   - 生产环境可替换为 OSS/MinIO，仅需改动 `ResourceService`。

> 以上 3 条是高层选型决策；更完整的 **12 条技术决策**（并发一致性、缓存、安全、可观测、Redis key 设计等）见 [`docs/DESIGN_DECISIONS.md`](DESIGN_DECISIONS.md)。

## 五、可扩展性

- 分层清晰，新增业务模块只需新增 Controller/Service/Mapper/Entity；
- 统一 `Result` 与全局异常处理，新增异常类型零侵入；
- 前端路由 + 角色元数据控制菜单显隐，后端 `@PreAuthorize` 方法级授权兜底。
