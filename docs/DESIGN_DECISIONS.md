# 技术设计决策记录（Design Decisions）

> 用途：记录项目里「**为什么这么做、为什么不那么做**」的技术权衡，是面试官追问「为什么」时的标准弹药。
> 每条按「**问题 → 候选方案 → 决策 → 理由 → 权衡**」组织。没有绝对正确的技术选型，只有「在什么约束下更合适」——本文档如实记录每个决策的边界与代价。
> 与 `docs/架构设计.md` 第四节互补：架构设计给出 3 条高层决策，本文档补全到 12 条并覆盖并发、缓存、安全、可观测等细节。

## 目录

1. 认证：Spring Security 过滤链 + JWT，而非手写拦截器
2. ORM：MyBatis-Plus，而非 JPA
3. 文件存储：本地磁盘，而非对象存储
4. 雷同检测：TF-IDF 字符 n-gram，而非大模型 / 词典分词
5. 学情预警：规则 + 阈值，而非规则引擎 / 机器学习
6. 埋点：AOP 异步落库，而非同步写入
7. 权限缓存：Caffeine 本地缓存，而非 Redis

9. 秒传去重：MD5，而非 SHA-256
10. 登录限流：固定窗口，而非滑动窗口
11. 并发一致性：业务校验 + 唯一索引 + Redis 锁，而非显式乐观/悲观锁

## 1. 认证：为什么用 Spring Security 过滤链 + JWT，而不是手写拦截器？

- **问题**：前后端分离后，服务端不再有 Session，需要一个无状态认证方案，同时要支持「不同角色能做什么」的细粒度控制。
- **候选**：① 手写 `HandlerInterceptor` 做登录拦截；② Spring Security 过滤链 + JWT。
- **决策**：**Spring Security 过滤链 + JWT**（保留 JWT 作为认证载体，替换原拦截器）。
- **理由**：拦截器工作在 `DispatcherServlet` 之后（MVC 层），只能做「是否登录」的粗粒度判断；过滤链在进入 MVC 之前就完成认证，能拿到完整请求上下文，并配合 `@EnableMethodSecurity` + `@PreAuthorize` 做**方法级**授权（如「只有 TEACHER 能 `submission:grade`」）。
- **权衡**：Security 上手门槛更高、配置更复杂；但换来的是权限模型可扩展、认证逻辑与业务解耦。

## 2. ORM：为什么用 MyBatis-Plus，而不是 JPA？

- **问题**：数据访问层选型，既要单表 CRUD 效率，又要能写复杂多表 SQL。
- **候选**：① JPA（Hibernate）自动建表/懒加载；② MyBatis-Plus。
- **决策**：**MyBatis-Plus**。
- **理由**：本项目的价值点恰好在**多表 JOIN + 聚合子查询**（课程联查教师名、作业统计提交/批阅数、提交四表 JOIN），MyBatis-Plus 保留原生 SQL 的灵活性；内置分页插件、`BaseMapper` 通用 CRUD 减少样板；更贴近国内企业主流栈。
- **权衡**：JPA 的「实体驱动建表、级联关系」更强，但复杂查询容易产生 N+1 或难以优化的生成 SQL，反而不利于答辩时讲清「这条 SQL 是怎么写的」。

## 3. 文件存储：为什么存本地磁盘，而不是对象存储（OSS/MinIO）？

- **问题**：课程资源（课件 PPT/PDF）存在哪。
- **候选**：① 本地目录 + `WebMvcConfigurer` 静态映射；② OSS/MinIO。
- **决策**：**本地磁盘**（教学演示场景）。
- **理由**：零外部依赖、开箱即用，答辩现场不依赖云账号/网络；通过静态映射即可访问。
- **权衡**：无法横向扩展、单机磁盘有上限。**已把存储层隔离在 `ResourceService` 内**，生产替换为 MinIO 只需改这一处，接口语义不变（这也是「文件存本地」可接受的原因——迁移成本被提前控住了）。

## 4. 雷同检测：为什么用 TF-IDF 字符 n-gram，而不是大模型 / 词典分词？

- **问题**：如何在不联网、不引重依赖的前提下，发现「改几个字就交」的雷同提交。
- **候选**：① 调用云端大模型做语义相似度；② 引入 jieba/HanLP 词级分词 + 句向量；③ 纯 Java 实现 TF-IDF + 字符 unigram/bigram + 余弦相似度。
- **决策**：**方案 ③（纯 Java TF-IDF + 字符 n-gram）**。
- **理由**：完全离线、学生文本不出服务器（隐私优势）；无词典分词意味着零外部依赖、可复现（不依赖词典版本）；「短文本雷同」本质是字面相似，TF-IDF 衡量词重要性 + 余弦衡量方向一致性，已能区分「改词抄袭」与「原创」。
- **权衡**：对「语义等价但用词完全不同的改写」召回有限（见 `docs/evaluation/雷同检测评测报告.md` 的局限），这是字符级方法的本质边界；但作为「辅助教师初筛」而非「自动判定」，够用且边界清楚。

## 5. 学情预警：为什么用规则 + 阈值，而不是规则引擎 / 机器学习？

- **问题**：教师需要「谁很久没登录、谁没交作业」的预警视图。
- **候选**：① 引入 Drools 规则引擎；② 训练 ML 预测模型；③ 阈值规则 + 服务层聚合。
- **决策**：**阈值规则 + 服务层聚合**（规则外置到 `application.yml`）。
- **理由**：预警规则就 2~3 条（N 天未登录 / N 天未提交），上 Drools 是「用大炮打蚊子」，增加认知与维护成本；ML 需要真实历史数据与标签，而项目当前只有演示数据，**硬上 ML 只会得到无评估的黑盒**，违背「诚实」原则。
- **权衡**：规则预警是「事后看板」而非「实时推送 / 预测」，能力有限；但这正是可扩展点（下一步可加 WebSocket 实时告警），而非当前该做的。

## 6. 埋点：为什么 AOP 异步落库，而不是同步写入？

- **问题**：学习行为埋点要在登录/看资源/交作业处记录，但**不能拖慢业务主流程**。
- **候选**：① 业务代码里同步 `insert`；② `@BehaviorLog` 注解 + AOP 切面同步写；③ AOP 切面 + `@Async` 异步写。
- **决策**：**③ AOP 声明式埋点 + 异步落库**（`ThreadPoolTaskExecutor`，`CallerRunsPolicy`）。
- **理由**：注解让业务方法只加一行、埋点逻辑统一收口（零侵入、不易漏）；异步把写库开销从请求主链路剥离，主接口不受埋点 IO 影响。
- **权衡**：异步意味着「埋点可能晚于业务提交」，极端情况下（进程崩溃）可能丢埋点；用 `CallerRunsPolicy` 保证线程池打满时**退化为同步执行、绝不静默丢数据**；埋点整体 `try/catch` 兜底，任何埋点异常不打断业务。

## 7. 权限缓存：为什么用 Caffeine 本地缓存，而不是 Redis？

- **问题**：JWT 过滤器每个请求都要从 RBAC 表查权限编码，DB 查询频繁。
- **候选**：① 每次查 DB；② 用 Redis 缓存权限编码；③ 用 Caffeine 进程内缓存。
- **决策**：**③ Caffeine 本地缓存**（TTL 300s，见 `PermissionCacheService`）。
- **理由**：权限编码是「高频读、低频改、数据量小」的典型场景，进程内缓存零网络开销、命中即内存返回；用 Redis 反而多一跳网络。
- **权衡**：Caffeine 是**单机**缓存，多实例部署时各实例各自缓存、无法共享失效；且账号状态仍**每请求复查 DB**（不缓存），所以「禁用账号即时失效」不受影响——这是有意为之的安全边界。

## 8. 下载鉴权：为什么用签名 URL，而不是登录态 header？

- **问题**：`/files/**` 静态下载怎么鉴权——前端 `window.open` / `<a href>` 无法带 `Authorization` 头。
- **候选**：① 让前端所有下载都带 JWT 头；② 生成带 `expires + sign` 的**签名 URL**。
- **决策**：**② HMAC-SHA256 签名 URL**（`?expires&sign`，密钥与 JWT 密钥分离）。
- **理由**：浏览器跳转下载天然不带自定义请求头，用签名 URL 把「授权」编码进链接本身，前端零改动即可下载；签名密钥独立于 JWT 密钥，**默认 JWT 密钥泄露不会导致伪造下载签名**。
- **权衡**：签名 URL 一旦外泄，在有效期（默认 1800s）内可被他人下载——所以 TTL 设短、且签名覆盖路径防篡改；这是「无 header 场景」下的务实折中。

## 9. 秒传去重：为什么用 MD5，而不是 SHA-256？

- **问题**：同一课件被反复上传浪费磁盘，需要内容去重指纹。
- **候选**：① MD5；② SHA-256。
- **决策**：**MD5**（纯 JDK `MessageDigest`）。
- **理由**：这里 MD5 用于**内容去重**（判断两文件是否相同），不是**密码学防篡改**；128 位 + 单机教学场景下碰撞概率可忽略，且 MD5 更快、更常见。
- **权衡**：若攻击者能「主动构造碰撞」则 MD5 不再安全——但去重场景的对手是「重复上传」而非「恶意碰撞」；防篡改应另用 SHA-256 + 签名（本项目下载签名已用 HMAC-SHA256 承担），二者职责分离。

## 10. 登录限流：为什么用固定窗口，而不是滑动窗口？

- **问题**：防暴力破解/撞库，对登录做频率限制。
- **候选**：① 固定窗口（Redis `INCR` + TTL）；② 滑动窗口（zset/令牌桶）。
- **决策**：**① 固定窗口**（账号 + IP 双维度，`max-attempts=5 / window=10min`）。
- **理由**：实现简单、只依赖 Redis 的 `INCR`+`EXPIRE` 两个原子命令，足够挡住「连续重试」这一主要威胁。
- **权衡**：固定窗口有「窗口边界双倍计数」的经典缺陷，且按来源 IP 计数在**校园网 NAT / 公司代理**下可能误伤同出口的正常用户（压测报告第四节已如实记录）；改进方向是「滑动窗口 + 每账号独立计数 + 验证码降级」，属于已知局限而非未察觉。

## 11. 并发一致性：为什么不用显式乐观锁 / 悲观锁？

- **问题**：批阅、提交、秒传上传这些写操作并发时如何保证一致性。
- **候选**：① 显式悲观锁（`SELECT ... FOR UPDATE`）；② 显式乐观锁（`@Version` 版本号）；③ 业务校验 + 数据库唯一索引 + 关键临界区 Redis 锁。
- **决策**：**③ 组合方案，按场景选择**：
  - **提交防重**：`submission` 表 `(assignment_id, student_id)` **唯一索引** + 业务校验——天然幂等，比任何锁都简单可靠；
  - **批阅**：`@Transactional` + InnoDB **行锁**（数据库层默认悲观锁语义）——单条更新的原子性由事务保证，无需显式锁；
  - **秒传去重 / 删除引用计数**：`res:file:{md5}` 的 **Redis 分布式锁**（`tryAcquire`/`release`）——因为秒传命中时「可能不落盘、无行可锁」，只能用「按内容指纹」的锁串行化「先查后写」临界区。
- **理由（为什么不用显式乐观锁）**：写冲突频率极低（一个教师批一条提交、同一文件重复上传是低频事件），乐观锁的「版本号 + 冲突重试」收益远小于成本；且给存量表加 `version` 列有迁移成本。
- **权衡**：Redis 锁有「进程崩溃锁未释放」风险，因此锁带 TTL（10s）；这是「够用且简单」与「完全正确」之间的有意取舍。

## 12. Redis key 设计与过期策略（汇总）

| 用途 | key 前缀 | 过期策略 | 目的 |
| --- | --- | --- | --- |
| 课程列表缓存 | `cache:course:all` | 基础 TTL 300s + 随机抖动 ≤60s | 防雪崩 |
| 看板聚合统计 | `cache:stats:overview` | 基础 TTL 60s + 随机抖动 | 热点读、防雪崩 |
| 空值缓存（防穿透） | 同上 key，写入空标记 | TTL 30s | 防缓存穿透 |
| 互斥锁（防击穿） | `{业务 key}:lock` | TTL 5s | 防缓存击穿 |
| 登录限流-账号 | `login:fail:user:{username}` | 窗口 10min | 防撞库 |
| 登录限流-IP | `login:fail:ip:{ip}` | 窗口 10min | 防暴力破解 |
| 秒传去重锁 | `res:file:{md5}` | TTL 10s | 串行化「先查后写」临界区 |

> 设计原则：① 所有 key 收敛到 `CacheKeys` 常量类，避免魔法字符串散落；② 所有 TTL 外置到 `application.yml`，可调不硬编码；③ 所有 Redis 操作 `try/catch` 兜底，Redis 宕机自动降级直查 DB，接口不 500。
