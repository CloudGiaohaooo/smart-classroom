## 一、项目总体概述

**一句话**：一个前后端分离的教学管理平台，覆盖「课程 — 作业 — 提交 — 批阅 — 资源」完整教学闭环。

| 维度 | 说明 |
| --- | --- |
| 后端 | Spring Boot 3.2.5 + Java 17 + MyBatis-Plus 3.5.7 + MySQL 8 |
| 前端 | Vue 3 + Vite + Element Plus + Pinia + Vue Router + Axios + ECharts |
| 认证 | JWT（jjwt 0.11.5，HS256）+ BCrypt 密码加密 |
| 架构 | 前后端分离 + 后端三层（Controller → Service → Mapper） |

**功能模块**：课程管理、作业列表、学生提交、作业批阅反馈、课程资源上传下载、数据概览仪表盘、登录鉴权与角色权限。

**代码规模**：后端 5 个实体、5 个 Mapper、5 个 DTO、8 个 VO、7 个 Service、7 个 Controller；前端 7 个页面视图。

## 三、数据库设计

### 3.1 十张表与关系（业务 5 + RBAC 4 + 埋点 1）

```
业务：
sys_user(用户)     1 ── N course(课程)          —— teacher_id
sys_user(用户)     1 ── N submission(提交)       —— student_id
course(课程)       1 ── N assignment(作业)       —— course_id
course(课程)       1 ── N course_resource(资源)  —— course_id
assignment(作业)   1 ── N submission(提交)       —— assignment_id
权限（RBAC）：
sys_user ──< sys_user_role >── sys_role ──< sys_role_permission >── sys_permission
埋点：
sys_user(用户)     1 ── N student_behavior(行为) —— AOP 零侵入写入
```

### 3.2 关键表字段与设计要点

**sys_user（用户表）**
- `username`（唯一索引 `uk_username`，加速登录查询并保证唯一）
- `password`（存 **BCrypt 密文**，绝不存明文）
- `role`（`ADMIN / TEACHER / STUDENT` 粗粒度角色，接口级细粒度权限由 RBAC 四表 + `@PreAuthorize` 承载）
- `status`（启用/禁用，登录时校验）

**course（课程表）**
- `teacher_id` 关联用户，建普通索引 `idx_teacher_id`
- `credit DECIMAL(3,1)`、`semester` 等业务字段

**assignment（作业表）**
- `course_id` 关联课程，索引 `idx_course_id`
- `deadline` 截止时间（提交时做业务校验）
- `total_score DECIMAL(5,2)` 满分

**submission（提交表）**
- `assignment_id`（索引）+ `student_id`（索引），两者是最高频的查询/关联字段
- `score` 得分、`feedback` 批阅反馈、`status`（`SUBMITTED / GRADED`）、`grade_time`
- 得分与反馈初始为 NULL，批阅后写入，用 `status` 区分状态

**course_resource（资源表）**
- `course_id`（索引）、`file_url` 文件访问路径、`file_size` 大小、`uploader_id`

### 3.3 索引设计思想（复试必问）

1. **唯一索引**：`username` —— 保证账号唯一 + 加速登录 `WHERE username = ?`。
2. **普通索引**：所有外键关联字段（`teacher_id`、`course_id`、`assignment_id`、`student_id`）—— 加速联表查询的 JOIN 条件和 WHERE 过滤。
3. **原则**：索引不是越多越好，写操作会维护索引带来额外开销；只在**高频查询字段**上建。
4. **外键约束的选择**：本项目在应用层通过业务代码保证引用关系，数据库层只建索引不建物理外键，便于演示、也便于未来分库分表。

## 四、后端核心技术详解

### 4.1 统一响应体 Result

所有接口返回同一结构，前端据此统一处理：

```json
{ "code": 200, "message": "操作成功", "data": { ... } }
```

```java
public class Result<T> {
    private int code;      // 200 成功 / 400 参数错误 / 401 未登录 / 403 无权限 / 404 不存在 / 500 系统错误
    private String message;
    private T data;
}
```

**价值**：前端不用针对每个接口写不同的解析逻辑；错误码统一、语义清晰。

### 4.2 全局异常处理 @RestControllerAdvice

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)               // 业务异常
    public Result<Void> handleBusiness(BusinessException e) {...}

    @ExceptionHandler({MethodArgumentNotValidException.class, BindException.class}) // 参数校验
    public Result<Void> handleValid(BindException e) {...}

    @ExceptionHandler(MaxUploadSizeExceededException.class)  // 上传超限
    public Result<Void> handleUploadSize(...) {...}

    @ExceptionHandler(Exception.class)                       // 兜底
    public Result<Void> handleException(Exception e) {...}    // 不把堆栈信息泄露给前端
}
```

**价值**：
- 业务代码里只需 `throw new BusinessException(...)`，不用到处 try-catch。
- 兜底 `Exception.class` 拦截未预期异常，**避免堆栈/敏感信息直接返回前端**（安全点）。

### 4.3 JWT 无状态认证（重点）

**为什么用 JWT**：前后端分离场景下，服务端不保存 Session，客户端每次请求自带令牌，服务端校验签名即可识别身份，天然适合横向扩展。

**JWT 结构**：`Header.Payload.Signature` 三段 Base64Url 编码，用 `.` 连接。HS256 用对称密钥做 HMAC-SHA256 签名。

**生成**（`JwtUtil.generateToken`）：

```java
Jwts.builder()
    .setSubject(username)              // 主题 = 用户名
    .claim("userId", userId)           // 自定义声明：用户 id
    .claim("role", role)               // 自定义声明：角色
    .setIssuedAt(now)
    .setExpiration(expire)             // 720 分钟
    .signWith(getKey(), SignatureAlgorithm.HS256)
    .compact();
```

**解析**（`JwtUtil.parseToken`）：`parseClaimsJws` 校验签名与过期时间，失败抛异常。

**认证过滤器 `JwtAuthenticationFilter`**（Spring Security 过滤链）：

```java
doFilterInternal:
  1. 从 Authorization: Bearer xxx 头解析 token
  2. 无 token → 放行（由 SecurityConfig 认证入口统一返回 401）
  3. 解析失败/过期 → 清空 SecurityContext，放行
  4. 成功 → 从 RBAC 表实时加载权限编码 → 写入 SecurityContext
          → 同时 UserContext.set(userId, username, role)  // 保留 ThreadLocal，业务零改动
finally:
  UserContext.clear()   // 防止线程池复用导致 ThreadLocal 内存泄漏
```

**为什么保留 ThreadLocal**：过滤器解析出的当前用户要传递给后续 Controller/Service 使用，而请求处理是单线程贯穿的，ThreadLocal 以「线程」为隔离单位，每个请求线程存一份，互不干扰；请求结束必须 `remove()` 释放。相较原拦截器方案，Security 过滤链额外把 RBAC 权限编码写入 `SecurityContext`，配合 `@PreAuthorize` 实现方法级授权。

**完整认证时序**：

```
登录：前端 POST /api/auth/login
        → AuthService 查用户 → BCrypt.matches 校验密码 → 签发 token
        → 返回 { token, user }
请求：前端 axios 拦截器给每个请求加 Authorization: Bearer <token>
        → JwtAuthenticationFilter 解析 token → SecurityContext + UserContext 写入
        → @PreAuthorize 方法级授权 → 业务代码 UserContext.getUserId() / getRole()
```

### 4.4 BCrypt 密码加密

```java
private final BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
// 注册/初始化：passwordEncoder.encode("123456")  存入数据库
// 登录校验：  passwordEncoder.matches(明文, 密文)
```

**为什么用 BCrypt 而不是 MD5/SHA**：
1. **单向哈希**：无法从密文还原明文。
2. **自带随机盐**：同一密码每次加密结果都不同，抵抗彩虹表攻击。
3. **计算成本可调**（cost factor），可随时间调高以对抗算力增长。

> 复试角度：为什么「加盐」能防彩虹表？→ 彩虹表是「明文→哈希」的预计算表，盐让每个用户的哈希输入都不同，攻击者无法用同一张表批量爆破。

### 4.5 事务 @Transactional（批阅场景）

```java
@Transactional(rollbackFor = Exception.class)
public void grade(Long id, GradeDTO dto) {
    Submission submission = submissionMapper.selectById(id);       // 1. 查提交记录
    // 2. 校验得分 <= 满分，否则抛业务异常
    submission.setScore(dto.getScore());       // 得分
    submission.setFeedback(dto.getFeedback()); // 反馈
    submission.setStatus("GRADED");            // 状态
    submission.setGradeTime(LocalDateTime.now()); // 时间
    submissionMapper.updateById(submission);   // 3. 更新（这四个字段必须一起成功）
}
```

**为什么需要事务**：批阅要同时更新「得分、反馈、状态、批阅时间」四个字段。若没有事务，中途出错会出现「分数改了但状态还是待批阅」的**中间态**，数据不一致。

**要点**：
- `rollbackFor = Exception.class` 显式声明：遇到任何异常（不只是 RuntimeException）都回滚。
- 事务是「要么全成功、要么全回滚」的原子性保证。
- 隔离级别默认 `Isolation.DEFAULT`，即继承数据库默认——MySQL InnoDB 默认是 **REPEATABLE READ（可重复读）**，通过 MVCC + 间隙锁也能避免幻读。

### 4.6 多表联查 + 聚合子查询（复试重点，必背 SQL）

**场景一：课程列表联查教师姓名（LEFT JOIN）**

```sql
SELECT c.id, c.course_name, u.real_name AS teacher_name
FROM course c
LEFT JOIN sys_user u ON c.teacher_id = u.id
WHERE (c.course_name LIKE CONCAT('%', #{keyword}, '%')
       OR c.course_code LIKE CONCAT('%', #{keyword}, '%'))
ORDER BY c.id DESC;
```

> 用 LEFT JOIN 而不是 INNER JOIN，是为了即使教师信息异常，课程记录也不会丢。

**场景二：作业列表统计「提交数 / 已批阅数」（相关子查询）**

```sql
SELECT a.id, a.title, c.course_name,
       (SELECT COUNT(*) FROM submission s WHERE s.assignment_id = a.id) AS submission_count,
       (SELECT COUNT(*) FROM submission s WHERE s.assignment_id = a.id AND s.status='GRADED') AS graded_count
FROM assignment a
LEFT JOIN course c ON a.course_id = c.id;
```

> 这里用**相关子查询**（子查询引用外层 a.id）在一条 SQL 里完成统计，避免 N+1 次查询。

**场景三：提交记录四表联查（最多 JOIN 的表）**

```sql
SELECT s.*, a.title AS assignment_title, a.total_score,
       c.course_name, u.real_name AS student_name
FROM submission s
LEFT JOIN assignment a ON s.assignment_id = a.id
LEFT JOIN course c ON a.course_id = c.id
LEFT JOIN sys_user u ON s.student_id = u.id
WHERE ...  -- 动态条件：assignmentId / studentId / status
ORDER BY s.id DESC;
```

**场景四：仪表盘按课程统计作业数（GROUP BY）**

```sql
SELECT c.course_name, COUNT(a.id) AS assignment_count
FROM course c
LEFT JOIN assignment a ON a.course_id = c.id
GROUP BY c.id, c.course_name
ORDER BY assignment_count DESC;
```

**为什么用 MyBatis-Plus 的 `@Select` 注解**：单表 CRUD 用 `BaseMapper` 自动完成；多表联查用 `@Select` + `<script>` 写原生 SQL，配合 `<if>` 做动态条件，兼顾开发效率与 SQL 灵活性。

### 4.7 分页

MyBatis-Plus 分页插件（`MybatisPlusConfig` 配置 `PaginationInnerInterceptor`），Mapper 方法签名接收 `Page<?>` 参数、返回 `IPage<T>`，自动在 SQL 末尾追加 `LIMIT` 并统计总条数。

### 4.8 文件上传与安全

```java
public void upload(Long courseId, String resourceType, MultipartFile file) {
    // 1. 唯一命名：UUID 去横线 + 原扩展名，避免重名覆盖
    String uuidName = UUID.randomUUID().toString().replace("-", "") + "." + ext;
    // 2. 按课程分目录：uploads/{courseId}/{uuid.ext}
    File dest = new File(uploadDir + courseId + "/" + uuidName);
    file.transferTo(dest);
    // 3. 元数据落库：file_url = /files/{courseId}/{uuid.ext}
}
```

**安全设计**：
- **UUID 重命名** → 用户无法预测文件名，防止**路径穿越**（`../../etc/passwd`）和**重名覆盖**。
- **按课程分目录** → 结构清晰、便于隔离。
- **大小限制** → `max-file-size: 100MB`，超限抛 `MaxUploadSizeExceededException`，由全局异常处理器统一兜底。
- **静态映射** → `WebConfig` 把 `/files/**` 映射到本地上传目录，前端通过 URL 直接访问，文件本身不在数据库里（数据库只存元数据）。

### 4.9 数据库初始化与演示数据

- **schema.sql**：`CREATE TABLE IF NOT EXISTS`（幂等），配合 JDBC URL 里的 `createDatabaseIfNotExist=true`，**首次启动自动建库建表**，无需手工执行 SQL。
- **DataInitializer**（`CommandLineRunner`）：应用启动后检测用户表为空则写入演示数据——账号 `admin / teacher / student / lisi / wangwu`（密码均 `123456`，BCrypt 加密）、3 门课程、3 个作业、4 条提交（含已批阅和待批阅），保证答辩现场开箱即演示。

## 五、前端核心技术详解

### 5.1 Axios 统一封装

```js
const request = axios.create({ baseURL: '/api', timeout: 15000 })

// 请求拦截器：自动附加 JWT
request.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截器：统一解包 Result
request.interceptors.response.use(response => {
  const res = response.data
  if (res.code === 200) return res.data          // 成功 → 直接返回业务数据
  if (res.code === 401) {                        // 登录过期 → 清空并跳转登录页
    localStorage.removeItem('token'); localStorage.removeItem('user')
    router.push('/login')
  }
  ElMessage.error(res.message || '请求失败')      // 其它错误 → 提示
  return Promise.reject(new Error(res.message))
})
```

**价值**：请求拦截器统一加 token，避免每个接口手写；响应拦截器统一解包 `Result`，业务代码拿到的是 `res.data` 裸数据；401 统一处理登录过期。

### 5.2 路由与权限

- **路由懒加载**：`component: () => import(...)`，按需加载减小首屏体积。
- **路由守卫**（`router.beforeEach`）：无 token 访问受保护页面 → 重定向 `/login`。
- **角色菜单**：路由 `meta.roles` 标记页面归属（如 `作业批阅 → ['TEACHER','ADMIN']`，`我的提交 → ['STUDENT']`），侧边栏菜单根据当前用户角色动态过滤；**后端在 Service 层做最终权限兜底**（前端控制显隐、后端保证安全）。

### 5.3 Pinia 状态管理

登录成功后把 `token`、`user` 存入 Pinia store 并同步到 `localStorage`，刷新页面不丢失登录态；退出时清除。

### 5.4 ECharts 数据概览

仪表盘调用 `StatsController` 的聚合接口，拿到各维度统计数 + 「按课程统计作业数」柱状图数据，用 ECharts 渲染。数据来自后端 `LEFT JOIN + GROUP BY` 实时聚合（见 4.6 场景四）。

## 六、安全设计（结合网络空间安全专业）

| 安全点 | 实现 | 防御的威胁 |
| --- | --- | --- |
| 密码存储 | BCrypt 单向哈希 + 随机盐 | 拖库后明文泄露、彩虹表 |
| 身份认证 | JWT 签名校验、过期时间 | 伪造身份、会话劫持（配合 HTTPS） |
| 越权防护 | 后端 Service 层按角色/用户 id 校验 | 前端绕过直接调接口 |
| 文件上传 | UUID 重命名 + 分目录 + 大小限制 | 路径穿越、重名覆盖、资源耗尽 |
| 信息泄露 | 全局异常处理器兜底，不返回堆栈 | 敏感信息/内部结构暴露 |
| SQL 注入 | MyBatis `#{}` 预编译参数占位 | 拼接 SQL 注入 |
| 跨域 | CORS 配置（开发放开，生产应收紧白名单） | 恶意站点跨域请求 |

**复试可强调的结合点**：作为网络空间安全专业学生，即便岗位是软件开发，也在项目里主动落实了「密码加密、无状态认证、上传安全、防信息泄露」等安全实践，体会到「安全要贯穿开发全生命周期」，而非事后补丁。

> 补充（体现思考深度）：JWT 是「签名」不是「加密」，Payload 只是 Base64Url 编码、任何人可解出内容，所以 **JWT 里只放 id/role 这类非敏感声明，绝不放密码**；生产环境密钥应放环境变量而非写死在配置文件。

## 七、可优化方向（体现工程视野）

## 八、复试高频考点速查（与《常见答辩问题与回答》配合使用）

| 技术点 | 核心一句话 |
| --- | --- |
| JWT | 无状态令牌 = 头部+载荷+签名；HS256 签名校验，服务端不存 Session |
| BCrypt | 单向哈希 + 随机盐 + 成本可调，防彩虹表 |
| ThreadLocal | 线程级变量隔离，请求结束必须 remove 防内存泄漏 |
| 事务 ACID | 原子性/一致性/隔离性/持久性，@Transactional 保证批阅原子性 |
| 隔离级别 | MySQL InnoDB 默认可重复读，MVCC+间隙锁防幻读 |
| LEFT JOIN | 返回左表全部行，右表无匹配补 NULL |
| 索引 | B+ 树加速查询，唯一索引防重，普通索引加速外键关联 |
| `#{}` vs `${}` | `#{}` 预编译防注入，`${}` 字符串拼接有注入风险 |
