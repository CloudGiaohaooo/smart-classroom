# 答辩问答逐字稿（照着念版）

> 使用说明：下面每个答案都是完整口语，可直接背诵/照着念。每条控制在 30~45 秒。
> 答题原则：先给结论，再展开，最后能落到项目里的一个具体接口 / 一条 SQL / 一段配置。
> 遇到没准备的追问，就诚实说"这块我做得还比较浅，下一步计划是……"。

## Q1：请简单介绍一下你做的这个项目？

这是一个前后端分离的在线教学管理平台，主要面向高校的教师和学生，覆盖课程管理、作业布置与提交、作业批阅反馈、课程资源上传四个模块。技术上，前端用 Vue3 加 Element Plus，后端用 Spring Boot 3，数据库是 MySQL 8，缓存用 Redis，认证用 JWT。这个项目的主线是工程规范和安全加固，另外我在工程实现上做了三个小尝试：智能辅助批阅、学习预警看板、还有资源 MD5 秒传去重。每个尝试我都有量化的评估：61 条自动化测试全绿，雷同检测在 100 对标注集上算了精确率和召回率，还做了压测，这些数据都在仓库里可以复现。

## Q2：为什么采用前后端分离？

前后端分离让前端和后端可以独立开发、独立部署，职责也更清晰——前端只负责展示和交互，后端只负责提供接口。这样以后如果要接移动端，后端的接口可以直接复用。当然它也会带来一些问题，比如跨域、鉴权、部署变复杂，这些我在项目里都做了对应的处理，比如用 vite 代理解决跨域、用 JWT 解决无状态鉴权。

## Q3：讲一下你的 JWT 认证流程。

用户登录时，后端先用 BCrypt 校验密码，通过之后就签发一个 JWT 令牌，载荷里只放用户 ID、用户名、角色这些非敏感信息，不放密码。前端拿到令牌后存到本地，之后每次请求都在请求头里带上 Authorization。后端有一个 JWT 过滤器，在请求进入控制器之前就解析令牌、把用户信息放到上下文里，再用 @PreAuthorize 注解做方法级授权。因为是无状态的，服务端不存会话，天然适合多实例扩展。

## Q4：三个工程尝试里，挑一个详细讲讲？

我讲智能辅助批阅。老师批改作业有两个痛点：一个是学生互相抄袭、改几个字就交，很难逐篇发现；另一个是相似质量的作业，要反复写一样的评语。我的做法是用纯 Java 实现 TF-IDF 加余弦相似度，先对同一作业下的所有提交做字符级分词，计算相似度，把疑似雷同的标出来；同时统计历史评语的高频词，给老师一键推荐评语。这个方案不依赖大模型、完全离线，学生文本不出服务器，没有隐私风险。实测同一批雷同提交的相似度在百分之九十九左右，全部命中。而且阈值不是拍脑袋定的：我用一套 100 对带真值标签的标注集，对两个阈值算了精确率、召回率和 F1——阈值 0.45 是 1.0、1.0、1.0，阈值 0.75 是 1.0、0.625、0.769，这样就有了评测依据。

## Q5：缓存穿透、击穿、雪崩，你是怎么防的？

穿透是查一个不存在的数据，每次都打到数据库，我用空值缓存，把"不存在"也缓存一个短时间的空标记。击穿是热点 key 过期的那一瞬间，大量请求同时打进来，我用互斥锁，只有一个线程去查库重建缓存，其余线程等待。雪崩是大量 key 在同一时刻过期，我给每个 key 的过期时间加一个随机偏移。另外所有 Redis 操作都有 try/catch 兜底，Redis 挂了就自动降级直查数据库，接口不会报错。

## Q6：你是怎么防止越权的？

我做了一轮横向越权审计，主要修了两类问题。一类是学生能读到全站所有提交，我在 Controller 层强制把查询条件里的学生 ID 改成当前登录用户本人。另一类是教师能跨课程操作，我加了一个统一的课程归属守卫类，批阅、改课、删课、传资源这些操作，都会先校验这个课程是不是属于当前这个教师。这两类修复我都用 MockMvc 测试固化了。

## Q7：事务在你项目里是怎么用的？

作业批阅是一个典型的、多个字段要一起改的场景，得分、反馈、状态、时间这四个字段必须一起生效。我用 @Transactional 保证这四个字段要么全部成功、要么全部回滚，不会出现只改了得分但状态没变这种中间状态。

## Q8：文件上传做了哪些安全处理？秒传去重怎么做？

上传时，我用 UUID 重命名文件避免覆盖，按课程分目录存储，做扩展名白名单防止上传脚本文件，下载走签名 URL 做鉴权。秒传是上传时用纯 JDK 计算文件的 MD5，如果已经存在相同内容的文件，就复用物理文件、只新增一条元数据；删除的时候按引用计数，多条记录共享同一个文件时不会误删。

## Q9：实习期间你做了什么？最大的收获是什么？

实习期间我主要参与了课程和作业列表前端页面的开发，以及资源上传、作业批阅接口的后端开发；实习之后，我主动把安全加固和三个工程尝试做了补强。最大的收获，是独立走通了从需求、设计、开发到测试、文档的完整流程，也养成了一个习惯——把安全当成开发的一部分，而不是事后再补。

## Q10：这个项目还有什么不足？下一步怎么优化？

不足主要是三点：它还是一个单体应用，没做微服务；高并发和分布式场景的经验还不够；预警目前是事后看板，不是实时推送。下一步我计划引入 MinIO 对象存储替代本地磁盘、用 WebSocket 把预警升级成实时告警，另外把覆盖率统计和更完整的压测补上。这些边界和下一步，我都写进了评估和局限两份文档里。

## Q11：你的日志是怎么做链路追踪的？

我给后端加了一个 TraceIdFilter，它在过滤链的最前面，给每个请求生成或者透传一个 X-Trace-Id，写进日志的 MDC 和响应头里。日志模板里加了 %X{traceId}，这样同一个请求打出来的所有日志，都能靠这个 id 串起来；前端报错的时候带着这个 id 回来，我就能定位到后端对应那几行日志。请求结束会在 finally 里把 MDC 清掉，防止线程池复用的时候串号。

## Q12：你做技术选型的时候，有没有「为什么不那么做」的考虑？

有，而且我专门整理了一份 12 条的设计决策记录。举两个例子：一个是雷同检测为什么不用大模型，因为要离线、学生文本不出服务器、而且要可复现，纯 Java 的 TF-IDF 就够了，代价是语义改写的召回有限，这个边界我记下来了。另一个是权限缓存为什么用 Caffeine 而不是 Redis，因为权限编码是高频读、低频改、数据量小，进程内缓存零网络开销，用 Redis 反而多一跳。每一条我都按「候选、决策、理由、权衡」四段记的，追问为什么我都能答。
